# CivilMind AI — Mandatory Execution Laws

This file is the single authoritative execution-policy reference for all GitHub Workers, coding agents and connected development tools working on CivilMind AI.

It must be read together with:

- `docs/MASTER_EXECUTION_PLAN.md`
- `docs/PROJECT_SPEC.md`
- `docs/PREMIUM_MODEL.md`
- `docs/AI_ARCHITECTURE.md`
- `docs/UI_GUIDELINES.md`
- `docs/FEATURES.md`
- `docs/ROADMAP.md`
- `docs/DASHBOARD_UI_SPEC.md`
- `docs/CHANGELOG.md`

If any older instruction conflicts with this file, the latest explicit owner instruction and this file take precedence.

---

## Law 1 — Mandatory Roadmap Execution

The complete approved roadmap, phases and sprints are binding. Always inspect the repository, latest commits and `docs/CHANGELOG.md`, identify the first genuinely incomplete sprint and resume from the exact incomplete implementation point. Do not restart completed work and do not rewrite the project from scratch.

## Law 2 — Free Official Knowledge

All official regulations, official resources, exam booklets, official questions, initial answer keys, final answer keys, official descriptive guides, global search and discipline/qualification filtering remain accessible without Premium. Premium must never be required to access public official knowledge.

## Law 3 — Premium Unlocks Intelligence

Premium unlocks AI intelligence, personalization, generation, advanced analytics, voice, document intelligence, Copilot, adaptive planning and professional automation. Premium sells intelligence, not files.

## Law 4 — Official and AI Content Separation

The UI and data model must clearly distinguish:

- official source text;
- official answer key;
- official descriptive answer;
- CivilMind AI explanation;
- AI inference;
- AI prediction;
- AI-generated practice content.

AI output must never be presented as an official legal or regulatory answer.

## Law 5 — Source-Grounded AI

AI responses must be retrieval-first and source-grounded whenever the requested subject is covered by approved sources. Show document, edition, page, clause and question citations when available. Never fabricate citations, pages, clauses, statistics, sources or official claims. State uncertainty clearly.

## Law 6 — AI-First Product and UI

The product must communicate that CivilMind AI is an intelligent engineering assistant, not a PDF archive. Preserve and implement the approved AI-first homepage, stronger Hero, Ask CivilMind AI, live analysis demo, Copilot, personalized dashboard, smart recommendations, Heat Maps, achievements, Premium previews and professional RTL responsive design.

## Law 7 — Sprint Definition of Done

A sprint is complete only when its real end-to-end user flow works and all required frontend, backend, data and access-control work are connected. Required checks must be run, failures fixed, code committed and pushed, Preview deployed or marked pending, verification performed when possible and `docs/CHANGELOG.md` updated.

## Law 8 — Continuous Sprint Execution

After completing a sprint, immediately begin the next valid sprint without waiting for normal user approval. Do not ask whether to continue. Pause only for a genuinely irreversible product decision, required credentials/authorization or a truly unavailable mandatory dependency with no safe alternative.

## Law 9 — Persistent «توسعه» Resume Command

Whenever the user sends only the Persian word `توسعه`, automatically:

1. read this file and GitHub Issue #21;
2. read `docs/CHANGELOG.md`;
3. inspect latest pushed commits and current branch;
4. detect the exact incomplete sprint and task;
5. resume from that point;
6. implement, test, commit and push meaningful work;
7. continue to the next sprint without repeating completed work.

Do not answer `توسعه` with confirmation, planning, an audit, browser status or “work started”.

## Law 10 — Zero Idle

Never become idle while meaningful safe work remains. A plugin, API, browser, provider, quota or external service becoming temporarily unavailable does not stop the whole project.

## Law 11 — Mandatory Multi-Tool Use

At the start of every run, inspect all connected tools, plugins, connectors and capabilities. Use every safe capability that can materially improve implementation, testing, deployment, validation, design, analytics, documentation, security or product quality. Do not ignore a newly available useful tool.

## Law 12 — Exact Dependency Queueing

When one tool is unavailable, record the limitation once and queue only the exact tasks that strictly depend on that tool. Immediately switch to other independent roadmap work. Do not block unrelated frontend, backend, testing, documentation, refactoring or content work.

## Law 13 — Automatic Return to Restored Tools

When a previously unavailable tool becomes available again, automatically return to the queued deployment, Preview, browser verification, screenshot, analytics, design or validation tasks, complete them, update `docs/CHANGELOG.md` and continue the roadmap.

## Law 14 — Continuous Tool Discovery

Continuously identify tools or integrations that could significantly improve the project. Recommend each useful missing tool with its priority, purpose and relevant phase/sprint. Continue development using current tools while awaiting owner approval.

## Law 15 — Automatic Adoption of Approved Tools

After the owner installs or connects a recommended tool, detect it and incorporate it into the relevant workflow without requiring the roadmap or previous instructions to be repeated.

## Law 16 — Authorization Handling

If an approved service requires login, OAuth or explicit permission, navigate to the authorization step when supported, pause only at the exact owner-approval screen and state only which service needs approval. After the owner authorizes it, resume from the interrupted task without restarting the sprint.

## Law 17 — No Wasteful Retries

Do not repeatedly retry an unavailable or quota-limited tool during the same run. Record it once, preserve the dependent continuation point and continue other work. Retry only when there is evidence that the tool may be available again or in a later execution.

## Law 18 — Deployment Pending Is Not Completion

If code, tests and build are complete but deployment or Cloud Browser verification is blocked, record the sprint as `Code Complete / Deployment Pending`, not fully completed. Continue independent work, and finalize the sprint when deployment and verification become available.

## Law 19 — Mandatory Completion Report

After a completed sprint, report only concrete completed work, including as applicable:

- phase and sprint;
- branch;
- commit SHA;
- Preview or live URL;
- changed files;
- typecheck, test, lint and build results;
- verification results;
- screenshot when visible UI changed;
- real blockers and queued tasks.

## Law 20 — Partial Artifacts Are Not Sprint Completion

A query, helper, schema, backend function, mock, audit, plan, standalone component, disconnected UI or opened browser tab is not a completed sprint. Do not stop after creating only one partial layer.

## Law 21 — Maximum Value Per Execution

Every execution must maximize meaningful project value rather than merely staying busy. When multiple safe independent tasks are available, prioritize work by:

1. unblocking critical dependencies;
2. completing end-to-end user-visible flows;
3. fixing security, access or data-integrity problems;
4. completing the current sprint;
5. improving product quality, reliability and conversion;
6. reducing future technical risk;
7. completing queued validation and deployment work.

Do not choose low-impact cosmetic or disconnected tasks when a higher-impact safe task can be completed.

## Law 22 — No Empty Status Responses

Do not respond only with:

- planning;
- “criteria registered”;
- “work started”;
- “browser opened”;
- “next step is”;
- a description of the existing UI;
- a tool or quota limitation;
- partial implementation progress.

While safe implementation work remains, continue working.

## Law 23 — Preserve Working Functionality

Do not remove or break working routes, integrations or features. Refactor incrementally. If a feature must move, preserve its behavior, document the relocation and verify the replacement flow.

## Law 24 — Truthful Data and Claims

Do not show fabricated pass rates, user counts, live activity, AI confidence, probabilities or performance claims. Use real measured data or clearly label content as Demo, Simulated, Estimated or AI-generated.

## Law 25 — Low-Token and Time-Limit Handoff

If execution time or token capacity is running low:

- finish the current safe atomic change where possible;
- run available checks;
- commit and push completed work;
- do not falsely mark an incomplete sprint complete;
- update `docs/CHANGELOG.md` with current phase, sprint, completed items, exact incomplete item, next file/flow, branch, commit SHA, Preview URL and queued tool-dependent tasks.

The next `توسعه` command must resume from that exact point.

# Mandatory Runtime Procedure

At the beginning of every execution:

1. Read `docs/EXECUTION_LAWS.md`.
2. Read `docs/MASTER_EXECUTION_PLAN.md`.
3. Read `docs/CHANGELOG.md`.
4. Inspect GitHub Issue #21 and latest commits.
5. Inspect all connected tools and newly available capabilities.
6. Identify the exact first incomplete sprint or queued validation task.
7. Select the highest-value safe work consistent with dependencies.
8. Execute continuously under all laws above.

# Valid Stopping Conditions

Execution may stop only when:

1. all approved roadmap work currently in scope is complete; or
2. explicit owner credentials/authorization are required; or
3. an irreversible owner decision is required; or
4. no meaningful safe implementation, testing, documentation, refactoring, validation or queued work remains.

Temporary quota limits, a single unavailable plugin, build failures, lint failures, test failures, implementation difficulty and ordinary refactoring needs are not valid reasons to remain idle.
